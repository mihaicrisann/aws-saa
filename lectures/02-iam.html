IAM: who may do what

Users, roles, policies, and the evaluation logic that decides every API call in AWS. The single most-tested topic on the exam.

Design Secure Architectures IAM STS SCP Policy evaluation

Every single action in AWS is an API call, and every API call goes through the same question: is this principal allowed to do this action on this resource under these conditions? IAM is the machine that answers it. Nothing else on the exam is tested this densely.

The four nouns

NounWhat it isUse it when
UserA long-lived identity with a password and/or access keys.A human, or legacy tooling that genuinely cannot assume a role. Rare in good designs.
GroupA bucket of users you attach policies to. Cannot be nested. Cannot be a principal.Organising human permissions.
RoleAn identity with permissions but no credentials. It is assumed, yielding temporary keys from STS.Almost always. EC2, Lambda, ECS tasks, cross-account access, federated humans.
PolicyA JSON document listing Effect / Action / Resource / Condition.Attached to identities (identity-based) or to resources (resource-based).
The default correct answer

If a question shows an EC2 instance, Lambda function or container needing to call an AWS service, the answer is an IAM role. Any option involving access keys in code, in environment variables, in userdata, or in a config file is wrong — every time, with no exceptions. This pattern alone is worth several marks.

Anatomy of a policy

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ReadOneBucketFromOffice",
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::reports",          // the bucket  → for ListBucket
      "arn:aws:s3:::reports/*"         // the objects → for GetObject
    ],
    "Condition": { "IpAddress": { "aws:SourceIp": "203.0.113.0/24" } }
  }]
}
Two-ARN gotcha

Bucket-level actions (s3:ListBucket, s3:GetBucketLocation) act on arn:aws:s3:::bucket. Object-level actions (GetObject, PutObject) act on arn:aws:s3:::bucket/*. A policy with only the first ARN produces "access denied" on downloads; only the second produces "access denied" on listing. Exam questions are built out of exactly this.

Useful condition keys to recognise: aws:SourceIp, aws:SourceVpce (came through a specific VPC endpoint), aws:PrincipalOrgID (any account in my Organization), aws:SecureTransport (HTTPS only), aws:MultiFactorAuthPresent, s3:x-amz-server-side-encryption (force encryption on upload).

Identity-based vs resource-based

Identity-basedResource-based
Attached toUser, group, roleThe resource itself: S3 bucket policy, SQS queue policy, SNS topic policy, KMS key policy, Lambda resource policy, VPC endpoint policy
Has a Principal?No — the identity is impliedYes — it names who is allowed
Cross-accountNeeds a role to assumeCan grant another account directly, without role assumption

For cross-account S3 access you need both sides to agree: the bucket policy allows the other account's principal, and that principal's identity policy allows the S3 action. Only within one account does an Allow on either side suffice.

Policy evaluation logic

Learn this order. It resolves nearly every "why is this denied?" question.

Evaluation, in order
1. Any explicit Deny anywhere?→DENY. Full stop. Nothing overrides it.
2. SCP (Organizations) allows it?→If not permitted by SCP → deny, even for the account root user.
3. Resource-based policy allows it?→Allow (this alone can be enough same-account).
4. Identity policy / permissions boundary / session policy allow?→Allow only if every applicable one allows.
5. Nothing said anything→Implicit DENY. Everything is denied by default.
SCPs are a filter, not a grant

A Service Control Policy attached to an Organizational Unit sets the maximum permissions for accounts in it. It never gives anyone access — it only takes it away. An account with AdministratorAccess under an SCP that denies ec2:* outside eu-west-1 genuinely cannot launch instances in Frankfurt. SCPs do not apply to the management account.

Related but distinct: a permissions boundary is attached to a single user or role and caps its maximum permissions. Standard use case: let developers create roles, but attach a boundary so they cannot create a role more powerful than themselves (privilege escalation).

Roles and STS

A role has two policies, and mixing them up is a common mistake:

  • Trust policy — who may assume this role. Its Principal is an account, a service (ec2.amazonaws.com), or an identity provider.
  • Permissions policy — what the role may do once assumed.

sts:AssumeRole returns temporary credentials (15 min – 12 h). Variants worth recognising:

APIFor
AssumeRoleCross-account and in-account role switching
AssumeRoleWithWebIdentityGoogle / Facebook / OIDC login — but for apps, Cognito Identity Pools is the recommended wrapper
AssumeRoleWithSAMLCorporate Active Directory / SAML 2.0 IdP federation
GetSessionTokenMFA-protected temporary credentials for an IAM user

IAM Identity Center (formerly AWS SSO) is the modern answer whenever a question mentions a workforce logging into many AWS accounts with existing corporate credentials. It fronts Organizations with permission sets and eliminates per-account IAM users.

Cross-account access: the ExternalId trap

When you grant a third party (a monitoring vendor, an auditor) a role in your account, the trust policy must require an sts:ExternalId. Without it, the vendor could be tricked into using their credentials against your account on someone else's behalf — the confused deputy problem. If an answer option mentions ExternalId in a third-party scenario, it is almost certainly correct.

Root user and account hygiene

  • The root user can do everything and cannot be restricted by IAM policies (only by SCPs, and not in the management account). Enable MFA, delete its access keys, and never use it day to day.
  • A handful of tasks require root: closing the account, changing the account name/email, changing support plan, restoring an unusable S3 bucket policy, registering as a seller.
  • IAM Access Analyzer flags resources shared outside your account or Organization, and can generate a least-privilege policy from CloudTrail history.
  • IAM credential report (account-wide CSV: key age, MFA, last used) vs Access Advisor (per-identity: which services were actually used). Both feed permission trimming.

Check yourself

A Lambda function must read from an S3 bucket in another account. What must be configured?
Two things. (1) The Lambda's execution role gets an identity policy allowing s3:GetObject on that bucket's objects. (2) The bucket's resource policy in the other account allows that role ARN. Cross-account needs both sides. If the bucket uses a customer-managed KMS key, the key policy must allow the role too — that's the third thing questions like to hide.
A developer has AdministratorAccess but cannot create an EC2 instance in us-east-1. Why?
Almost certainly an SCP on their Organizational Unit denying that Region, or a permissions boundary on their user. An explicit deny at any layer wins over any Allow.
What's wrong with baking an access key into an EC2 AMI so the app can write to DynamoDB?
Everything. Keys are long-lived, they travel with every copy of the AMI, they cannot be rotated without a rebuild, and anyone who reaches the instance gets them. Attach an instance profile / IAM role — the SDK picks up rotating temporary credentials automatically from the instance metadata service.
A policy allows s3:GetObject on arn:aws:s3:::logs. Downloads fail. Fix?
Wrong ARN level. Object actions need arn:aws:s3:::logs/*. Add it (keep the bare bucket ARN too if ListBucket is needed).

Take away

  1. Compute needs AWS access → IAM role. Never access keys. This is the highest-yield rule on the exam.
  2. Explicit Deny beats everything; absence of an Allow is a deny; SCPs cap but never grant.
  3. Resource-based policies carry a Principal and enable cross-account access without assuming a role — but for S3 cross-account you still need the caller's identity policy to allow it.
  4. S3 policies need two ARNs: bucket for listing, bucket/* for objects.
  5. Trust policy = who can assume. Permissions policy = what they can then do.
  6. Third-party cross-account access → require sts:ExternalId. Workforce SSO across many accounts → IAM Identity Center.
