Serverless and containers

Lambda's real limits, ECS vs EKS vs Fargate, API Gateway, and the question the exam is really asking when it says 'no servers to manage'.

Design High-Performing Architectures Design Cost-Optimized Architectures Lambda Fargate ECS API Gateway

"No servers to manage", "scale to zero", "pay only for what you use" — the exam has a small vocabulary for serverless, and each phrase points at a short list of services. This lecture is about knowing the list and, more importantly, the limits that make an option wrong.

Cold starts

The fix the exam wants is Provisioned Concurrency — keeps N environments initialised and warm, eliminating cold starts for latency-sensitive APIs. Reserved concurrency is a different thing: it caps (and guarantees) how much of the account's concurrency pool a function may use — used to stop one function starving the others, or to protect a downstream database from being hammered.

Lambda in a VPC: needed only to reach private resources (RDS, ElastiCache, private ALBs). Attaching it to a VPC means the function has no internet access unless the subnet routes through a NAT Gateway, and calls to AWS services should go via VPC endpoints. This trade-off is a recurring question.

Error handling: synchronous invokes return the error to the caller. Asynchronous invokes retry twice, then send the event to a Dead Letter Queue or an on-failure destination. Event-source-mapping (SQS, Kinesis, DynamoDB Streams) has its own retry and failure destination settings.

Two roles in ECS, and people mix them up

The task execution role lets ECS itself pull the image from ECR and write logs to CloudWatch. The task role is what your application code uses to call AWS services (S3, DynamoDB). If the app gets access denied talking to S3, it's the task role. If the task won't even start because it can't pull the image, it's the execution role.

API Gateway

The managed front door for APIs: auth, throttling, caching, validation, versioning via stages.

TypeNotes
HTTP APICheaper (~70% less), lower latency, fewer features. The default for simple Lambda/HTTP proxying with JWT auth.
REST APIFull feature set: API keys + usage plans, request/response transformation, caching, WAF, resource policies, private endpoints.
WebSocket APITwo-way, stateful connections — chat, live dashboards.

Authorisation options, in the order the exam presents them: IAM (internal/service-to-service, SigV4), Cognito user pools (app users signing in), Lambda authorizer (custom/third-party token logic), API keys + usage plans (rate-limit and meter per customer — not authentication on its own).

Throttling and back-pressure

"Protect the backend from traffic spikes" → API Gateway throttling (429s) and caching at the stage level. If the question instead wants no request lost, the answer is to buffer with SQS and process asynchronously.

The rest of the serverless kit

  • Step Functions — visual state machine for orchestrating multi-step workflows, with retries, branching, parallelism and human approval. The answer for "coordinate long-running or multi-step processes", and how you exceed Lambda's 15 minutes without EC2. Standard workflows: up to a year, exactly-once. Express: up to 5 min, very high volume, at-least-once.
  • AppSync — managed GraphQL, with real-time subscriptions and offline sync. Cue word: GraphQL.
  • Amplify — hosting plus backend scaffolding for web/mobile front-ends.
  • Elastic Beanstalk — not serverless, but the "just deploy my code, AWS handles capacity/LB/scaling, and I still want access to the EC2 instances" answer. You keep full control of the underlying resources; it is free (you pay for what it provisions).
  • Lambda@Edge / CloudFront Functions — run code at edge locations. CloudFront Functions: sub-millisecond, JS only, viewer request/response, for header manipulation and redirects. Lambda@Edge: heavier, can also run at origin request/response, can make network calls.

Check yourself

A data conversion job runs 45 minutes per file, triggered by S3 uploads. Design it.
Lambda is out (15-minute ceiling). S3 event → SQS → ECS/Fargate tasks or an AWS Batch job (Spot-backed for cost). A small Lambda may still act as the trigger that submits the job.
An API backed by Lambda has 2–3 s latency on the first request after idle periods.
Cold starts. Enable Provisioned Concurrency on the alias. Secondary wins: smaller deployment package, avoid heavy init outside the handler, and prefer a lighter runtime.
A Lambda in a VPC times out calling a public third-party API. Why?
VPC-attached Lambdas have no internet route by default. Put the function in private subnets whose route table points 0.0.0.0/0 at a NAT Gateway. (Putting a Lambda in a public subnet does not give it internet — it has no public IP.)
Which costs less for a low-traffic REST API in front of Lambda, and what do you give up?
HTTP API — roughly 70% cheaper and faster. You give up API keys/usage plans, request/response transformation, response caching, resource policies and direct WAF integration. If the question requires any of those, use a REST API.

Take away

  1. Lambda's 15-minute limit is the most useful elimination rule in the compute domain.
  2. Provisioned concurrency kills cold starts; reserved concurrency caps blast radius.
  3. Fargate is a launch type for ECS/EKS — "containers without managing instances".
  4. ECS task execution role pulls images; task role is what your code uses.
  5. Step Functions orchestrates; API Gateway fronts, throttles and caches; SQS buffers.
  6. A VPC-attached Lambda needs a NAT Gateway for the internet and VPC endpoints for AWS APIs.
