Block and file storage

EBS volume types and their IOPS ceilings, instance store, EFS, the FSx family, and how data gets in from on-premises.

Design High-Performing Architectures Design Resilient Architectures EBS EFS FSx DataSync Snow

Three shapes of storage, and the exam mostly tests whether you can tell which shape a scenario needs. Block = a virtual disk attached to one machine (EBS). File = a shared filesystem many machines mount (EFS, FSx). Object = S3. Pick the shape first, then the product.

EBS volume types

TypeMax IOPS / throughputUse for
gp3 (SSD)3,000 IOPS & 125 MB/s baseline, up to 16,000 IOPS / 1,000 MB/s — provisioned independently of sizeThe default. ~20% cheaper than gp2 and you tune IOPS without growing the disk.
gp2 (SSD)3 IOPS per GB, max 16,000 — you must grow the volume to get IOPSLegacy. If a question describes buying a bigger volume purely for IOPS, the answer is "switch to gp3".
io2 Block Express (SSD)Up to 256,000 IOPS, 4,000 MB/s, 99.999% durabilityCritical databases needing sustained high IOPS and sub-ms latency. Supports Multi-Attach (one volume, up to 16 instances in the same AZ, cluster-aware filesystem required).
st1 (HDD)500 MB/s throughput-optimisedBig sequential reads: log processing, data warehouse, streaming. Cannot be a boot volume.
sc1 (HDD)250 MB/s, cheapestCold, rarely accessed. Not a boot volume.
EBS facts that decide questions
  • An EBS volume is zonal — one AZ, and (except io2 Multi-Attach) attached to one instance at a time. "Many instances need the same files" is never EBS.
  • Snapshots are incremental and stored in S3, are Regional, and can be copied cross-Region (that's how you do EBS DR) and shared with other accounts.
  • Snapshot of an encrypted volume is encrypted; a volume restored from it is encrypted. To encrypt an existing unencrypted volume: snapshot → copy the snapshot with encryption enabled → create a new volume → swap.
  • You can resize and change type live (elastic volumes); the filesystem still needs extending inside the OS.
  • Data Lifecycle Manager automates snapshot schedules and retention. Recycle Bin protects against accidental snapshot deletion.

Instance store

Physically attached NVMe on the host: the highest possible IOPS, and ephemeral — data is gone when the instance stops, hibernates or terminates (it survives a reboot). Right answer for scratch space, caches, buffers, and the local disks of a distributed system that replicates itself. Wrong answer for anything that must persist.

EFS

Managed NFS: a filesystem many EC2 instances across many AZs mount at once, growing and shrinking automatically. Linux only.

  • Storage classes: Standard (multi-AZ) and One Zone (cheaper, single AZ). Lifecycle management moves untouched files to Infrequent Access or Archive.
  • Performance modes: General Purpose (default, lowest latency) vs Max I/O (higher throughput, higher latency, thousands of clients).
  • Throughput modes: Elastic (default, scales automatically), Provisioned, Bursting.
  • Access is controlled by security groups on the mount targets, plus IAM and EFS access points. Encryption at rest via KMS, in transit via TLS.
  • Lambda can mount EFS — the way a function gets more than 10 GB of shared, persistent working storage.
The single most reliable cue

"Multiple EC2 instances need concurrent access to the same files" → EFS. It is right nearly every time, and it eliminates EBS immediately. Add "Windows / SMB / Active Directory" and it becomes FSx for Windows File Server instead.

Wire or lorry? Do the arithmetic

A rough rule: over a 1 Gbps link you move about 10 TB per day. So 100 TB is roughly 10 days of saturated link — Snowball is usually faster and cheaper. Under ~10 TB, or when the pipe is fat and idle, DataSync over the network wins. Exam questions supply the bandwidth and the volume precisely so you can make this call.

Picking the shape

Storage decision list
One instance, needs a disk / boot volume / database files→EBS (gp3 default, io2 for heavy DB IOPS)
Many Linux instances, same files, concurrently→EFS
Windows / SMB / Active Directory→FSx for Windows File Server
HPC or ML training against S3 data→FSx for Lustre
Temporary scratch, maximum IOPS, loss acceptable→Instance store
Unstructured objects, web-scale, HTTP access→S3
On-prem app must keep its file share→Storage Gateway (File)

Check yourself

A CMS on 6 EC2 instances behind an ALB must all see uploaded images immediately.
EFS, mounted by every instance. (In a redesign, S3 plus CloudFront is even better — but EFS is the drop-in answer when the app expects a POSIX filesystem.) EBS cannot do this.
A gp2 volume is 500 GB purely to reach 1,500 IOPS. Reduce cost.
Move to gp3 and provision IOPS independently of capacity — shrink the volume to what the data actually needs and set 3,000 baseline IOPS, which is included. gp3 is also ~20% cheaper per GB.
300 TB must move to S3. The site has a 500 Mbps link already 60% used.
Usable ~200 Mbps ≈ 2 TB/day → about 150 days. Use Snowball Edge devices (several in parallel). DataSync over that link is not viable.
An analytics cluster needs a POSIX filesystem with hundreds of GB/s throughput over data already in S3.
FSx for Lustre, linked to the S3 bucket so objects appear as files and results can be written back.

Take away

  1. Decide the shape first: one machine → block; many machines → file; over HTTP → object.
  2. gp3 is the default EBS type; io2 Block Express for heavy databases; st1/sc1 for sequential HDD and never as a boot volume.
  3. EBS is one-AZ, one-instance (bar io2 Multi-Attach). Snapshots are incremental, Regional, and the way you move or DR a volume.
  4. Instance store = fastest and ephemeral. Never for persistent data.
  5. "Shared access from multiple instances" → EFS; add Windows/SMB → FSx for Windows; add HPC/ML → FSx for Lustre.
  6. Migration: DataSync over the wire, Snowball when the wire would take too long, Storage Gateway when on-prem must keep its protocol.
