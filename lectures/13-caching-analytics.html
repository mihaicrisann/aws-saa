Caching and analytics

ElastiCache Redis vs Memcached, Redshift, Athena, Glue, Kinesis, EMR, OpenSearch. Mostly a service-recognition exercise — learn the cues.

This lecture is mostly service recognition. You will rarely be asked to design a data pipeline in depth — you will be asked which of four services fits a one-line description. Learn the cue words.

The tiebreaker

If the question mentions persistence, replication, high availability, sorted sets, or pub/sub → Redis. If it stresses a simple, multi-threaded, horizontally-scaled cache where losing data is fine → Memcached. In doubt, Redis.

Caching strategies worth naming: lazy loading (cache-aside — read miss fetches from the DB and populates; cache may be stale, but only requested data is cached) and write-through (every write updates the cache — always fresh, but caches data nobody reads). TTLs bound staleness in both.

Kinesis Data Streams vs Firehose

This pair is asked constantly, so be precise:

Data StreamsData Firehose
LatencyReal time (~200 ms)Near real time (60 s buffer minimum)
Storage / replayRetains 1–365 days, replayableNo storage — it delivers and forgets
ManagementYou size shards (or use on-demand)Fully managed, auto-scales
ConsumersMany, independentOne destination
Answer to"Multiple applications process the same stream", "custom real-time logic""Just get this stream into S3/Redshift with the least effort"
Kinesis vs SQS

Both move messages, and the exam offers them as alternatives. SQS = a work queue: one consumer group, message deleted after processing, no ordering guarantee (unless FIFO), no replay. Kinesis = an ordered log: ordered within a shard, retained and replayable, and many independent consumers read the same records. "Replay", "ordering", "multiple consumers", "real-time analytics" → Kinesis. "Decouple and process each job once" → SQS.

Check yourself

Analysts want to run occasional SQL over 5 TB of JSON logs already in S3. Minimal setup, minimal cost.
Athena (with a Glue crawler to build the catalog). Then cut the bill by converting to Parquet and partitioning — Athena charges per TB scanned, and columnar + partitioned often reduces that by 90%+. Redshift would mean provisioning a cluster for occasional queries.
The simplest way to get a streaming feed into S3 with no shard management.
Data Firehose. Choose Data Streams only if you need sub-second latency, replay, or multiple independent consumers.
A database is at 100% CPU serving the same product-catalogue query thousands of times a second.
Put ElastiCache for Redis in front with a lazy-loading (cache-aside) strategy and a sensible TTL. Add read replicas if writes remain the bottleneck.
Users must search across millions of documents by free text, with a dashboard over the results.
Amazon OpenSearch Service — full-text search plus built-in dashboards. Athena and Redshift do SQL, not relevance-ranked text search.

Take away

  1. Redis unless the question specifically wants a simple, disposable, multi-threaded cache.
  2. Athena = SQL on S3, pay per scan; Parquet + partitioning is the cost answer. Redshift = warehouse for heavy repeated analytics.
  3. Glue = ETL + the Data Catalog that Athena and Redshift Spectrum read.
  4. Kinesis Data Streams = real time, replay, many consumers. Firehose = managed delivery, near real time, one destination.
  5. Kafka → MSK. Spark/Hadoop → EMR. Full-text search → OpenSearch. Dashboards → QuickSight.
  6. Replay/ordering/multiple consumers → Kinesis. Process-once work queue → SQS.
