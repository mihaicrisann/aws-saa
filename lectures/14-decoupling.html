Decoupling: queues, topics, events

SQS, SNS, EventBridge, Step Functions and Amazon MQ. 'Decouple' is exam code for a specific short list of answers.

Design Resilient Architectures Design High-Performing Architectures SQS SNS EventBridge Step Functions

When a question says "decouple", "the downstream system can't keep up", or "messages must not be lost when a component fails", it has narrowed the answer to four services. Knowing which of the four is the whole game.

The four shapes

ServiceShapeCue
SQSQueue — one message, one consumer, pulled"Buffer", "absorb spikes", "process each job once", "worker fleet"
SNSTopic — one message, many subscribers, pushed"Fan out", "notify multiple systems", "send an email/SMS alert"
EventBridgeEvent bus — routed by content-based rules"React to AWS service events", "SaaS integration", "route by event content", "schedule (cron)"
Step FunctionsState machine — ordered, stateful workflow"Multi-step", "orchestrate", "retries and branching", "human approval"

SQS in detail

  • Standard queues: near-unlimited throughput, at-least-once delivery, best-effort ordering. Your consumer must be idempotent — that word in a question means "standard queue is acceptable".
  • FIFO queues: exactly-once processing and strict ordering within a message group, up to 300 msg/s (3,000 batched, higher with high-throughput mode). Name must end in .fifo. Choose only when ordering or de-duplication is explicitly required — it is slower and more constrained.
  • Visibility timeout (default 30 s, max 12 h): after a consumer receives a message it is hidden. If the consumer doesn't delete it in time, it reappears and may be processed twice. "Messages are being processed more than once" → increase the visibility timeout (or extend it in-flight).
  • Dead Letter Queue: after maxReceiveCount failed attempts, the message moves aside for inspection instead of blocking the queue forever. Always the right answer for "poison messages".
  • Long polling (ReceiveMessageWaitTimeSeconds up to 20 s) reduces empty responses and cost versus short polling.
  • Retention 1 minute – 14 days (default 4 days). Delay queues postpone delivery up to 15 minutes.
  • Message size 256 KB; the Extended Client Library stores larger payloads in S3 and passes a pointer.
  • Encryption with KMS; access via queue policies (resource-based).
The signature SQS pattern

Producers → SQS → Auto Scaling group of workers, scaled on the CloudWatch metric ApproximateNumberOfMessagesVisible (ideally as a backlog-per-instance target-tracking policy). This single diagram answers "handle unpredictable spikes without losing requests and without over-provisioning" — which appears in some form on almost every exam.

SNS and fan-out

Publish once to a topic; every subscriber gets a copy. Subscribers: SQS queues, Lambda, HTTP/S endpoints, email, SMS, mobile push, and Data Firehose. Message filtering policies let each subscriber receive only the messages it cares about. FIFO topics pair with FIFO queues for ordered fan-out.

          ┌──► SQS ──► image resizing workers
Upload ──► SNS ──► SQS ──► virus scanning workers
          └──► Lambda ──► write metadata to DynamoDB
Why SNS → SQS, not SNS → Lambda directly?

The fan-out pattern puts a queue between the topic and each consumer so that (a) messages are durably buffered if a consumer is down, (b) each consumer scales and retries independently, and (c) you can replay. If an option offers "SNS to multiple SQS queues" for a multi-consumer scenario with reliability requirements, it is usually the intended answer.

EventBridge

A bus rather than a queue. Its distinguishing capabilities:

  • Native AWS service events — EC2 state changes, S3 events, CodePipeline stages, Health events. "When an EC2 instance terminates, do X" is EventBridge.
  • Content-based rules that match on any field of the JSON event, routing to up to 5 targets each.
  • Scheduler — cron and rate expressions. Whenever a question says "run something every night at 2 a.m.", EventBridge Scheduler is the modern answer.
  • Partner event sources (Datadog, Zendesk, Shopify…) and custom buses per application.
  • Schema registry and archive + replay of past events.
  • Pipes for point-to-point source → filter → enrich → target integrations.

Step Functions and Amazon MQ

Step Functions coordinates services into a workflow defined as JSON states: Task, Choice, Parallel, Map, Wait, Retry/Catch. It keeps the state, so you don't hand-roll orchestration inside Lambdas. Standard workflows run up to a year with exactly-once execution and full history; Express workflows run up to 5 minutes at very high volume with at-least-once semantics. Use it for order processing, ETL orchestration, human-approval steps, and anything that needs to run longer than a single Lambda.

Amazon MQ is managed ActiveMQ/RabbitMQ. It exists for one exam purpose: a migrating application that already speaks a standard protocol — JMS, AMQP, MQTT, STOMP, OpenWire. Cue: "lift-and-shift without rewriting the messaging code". A greenfield design should use SQS/SNS instead.

Decision list

Which integration service?
Buffer work so spikes don't overwhelm the backend→SQS
Strict ordering or no duplicates→SQS FIFO
One event, several independent systems must react→SNS fan-out to SQS queues
React to an AWS service event, or route by event content→EventBridge
Run something on a schedule→EventBridge Scheduler
Multi-step process with retries, branching, waits→Step Functions
Existing app speaks JMS / AMQP / MQTT→Amazon MQ
Replay, ordering, and multiple consumers over a real-time firehose→Kinesis Data Streams

Check yourself

An order service occasionally gets 50× normal traffic and the payment backend falls over. No order may be lost.
Put SQS between them. The queue absorbs the spike; the payment workers run in an Auto Scaling group scaled on queue depth and drain the backlog at their own pace.
The same messages are being processed twice by workers whose jobs take about 90 seconds.
The visibility timeout (default 30 s) is shorter than the processing time, so the message reappears mid-job. Raise it above the worst-case duration, or call ChangeMessageVisibility as the job runs. Make the consumer idempotent regardless.
A few malformed messages keep failing and are blocking the queue.
Attach a Dead Letter Queue with a maxReceiveCount of, say, 3. Failing messages move aside for investigation and the queue keeps flowing.
When a file lands in S3, three separate teams' systems must each process it, independently and reliably.
S3 event → SNS topic → three SQS queues, one per team, each with its own consumers. (Routing via EventBridge to three targets is also valid; the queues are what make it reliable when a consumer is down.)

Take away

  1. SQS buffers and levels load; SNS fans out; EventBridge routes and schedules; Step Functions orchestrates.
  2. Standard SQS = at-least-once and unordered, so make consumers idempotent. FIFO only when ordering or de-duplication is stated.
  3. Duplicate processing → visibility timeout too short. Poison messages → dead letter queue.
  4. Scale workers on ApproximateNumberOfMessagesVisible, not CPU.
  5. SNS → SQS fan-out is the durable multi-consumer pattern.
  6. Amazon MQ exists for migrations of apps already speaking JMS/AMQP/MQTT.
