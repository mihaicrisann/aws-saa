Resilience and disaster recovery

RTO and RPO, the four DR strategies and their cost order, and how to read a resilience question in ten seconds.

Design Resilient Architectures Design Cost-Optimized Architectures RTO RPO Pilot light Warm standby Multi-region

Resilience questions are formulaic once you know the vocabulary. The scenario states a recovery objective, and the objective picks the strategy, and the strategy picks the services. Learn the mapping and these become the fastest questions on the paper.

RTO and RPO

MeasuresDowntime you can tolerateData loss you can tolerate
Reads as"How long until we're back?""How much recent work may we lose?"
Driven byHow much infrastructure is already runningHow often you replicate or back up

The single most useful sentence

Low RPO is bought with replication frequency; low RTO is bought with pre-provisioned capacity. "We can lose at most 5 minutes of data" is an RPO statement → continuous or near-continuous replication. "We must be back within 10 minutes" is an RTO statement → something must already be running.

Pilot light vs warm standby

Constantly confused. Pilot light: the database replicates but no application servers are running — you must launch them during failover. Warm standby: a small but complete and running stack that you scale up. Rule of thumb: if the question says "a scaled-down version of the environment is always running", that's warm standby. If it says "data is replicated and servers are launched from AMIs when needed", that's pilot light.

The exam usually wants the cheapest strategy that still meets the stated objectives. Multi-site is rarely correct unless the requirement is near-zero RTO/RPO or the question explicitly says cost is not a concern.

Designing so failure doesn't matter

  • Stateless compute. Any instance can serve any request; instances are cattle, not pets.
  • Loose coupling. A queue between components means a failure downstream becomes a backlog, not an outage.
  • Graceful degradation. Serve cached or reduced functionality rather than an error.
  • Idempotency and retries with exponential backoff and jitter. AWS SDKs do this; the exam expects the words.
  • Health checks that test the real dependency chain, so a broken instance is removed rather than kept.
  • Automate recovery — ASG replacement, Multi-AZ failover, Config remediation. If the answer requires a human to notice, it is usually the weaker option.
  • Test it. AWS Fault Injection Service runs controlled chaos experiments; game days prove the runbook.
Backups are not DR

A backup that has never been restored is a hypothesis. AWS Backup gives central policy, cross-Region and cross-account copies, and Backup Vault Lock for immutability — which is also the answer to "protect backups from a malicious administrator or ransomware".

Reading a resilience question in ten seconds

Requirement → answer
"Survive an AZ failure"→Multi-AZ within one Region. Not a second Region.
"Survive a Region failure"→Second Region + cross-Region replication + Route 53 failover
"RTO hours, RPO hours, cheapest"→Backup and restore
"RTO ~30 min, minimal ongoing cost"→Pilot light
"RTO minutes, and cost still matters"→Warm standby
"Near-zero RTO and RPO, serve users in both Regions"→Active-active (Aurora Global DB / DynamoDB Global Tables)
"No manual intervention"→Prefer whichever option fails over automatically

Check yourself

RPO 15 minutes, RTO 4 hours, budget tight. Which strategy?
Pilot light: a cross-Region database replica (or frequent snapshot copies) satisfies the 15-minute RPO, while launching compute from AMIs during the incident easily fits inside a 4-hour RTO — with almost no idle spend. Warm standby would meet it too, but costs more than required.
An app runs in one AZ with a single NAT Gateway and min=1. Name the failure modes.
Three: the ASG cannot survive losing the one instance without downtime; the single NAT Gateway is a zonal single point of failure for all egress; and the whole stack dies with its AZ. Fix: subnets and ASG across ≥2 AZs, min=2, one NAT Gateway per AZ, RDS Multi-AZ.
Failover between Regions must take seconds, and clients cache DNS aggressively.
Global Accelerator. Its two anycast IPs never change, so failover happens in the network within seconds and does not depend on client DNS caching or TTLs.
Ransomware encrypted production and then deleted the backups. What should have been in place?
Immutable, isolated backups: AWS Backup with Vault Lock, copies in a separate account and Region, plus S3 Object Lock in compliance mode and MFA delete for object data.

Take away

  1. RPO = data loss, bought with replication frequency. RTO = downtime, bought with running capacity.
  2. Four strategies in cost order: backup & restore → pilot light → warm standby → multi-site active-active. Choose the cheapest that meets the numbers.
  3. Pilot light replicates data only; warm standby keeps a small full stack running.
  4. "AZ failure" is an in-Region problem — Multi-AZ, ≥2 AZs, one NAT per AZ, min 2 instances.
  5. Cross-Region: S3 CRR, Aurora Global Database, DynamoDB Global Tables, snapshot copies, StackSets, Route 53 failover.
  6. Prefer automatic recovery over anything needing a human, and make backups immutable and cross-account.
