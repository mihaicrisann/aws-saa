A load balancer spreads traffic across healthy targets; an Auto Scaling group keeps the right number of them alive. Together they are what the exam means by "highly available and elastic", and they appear in a large share of resilience questions.

Three question-cues that decide instantly

"Static IP addresses to whitelist in a partner firewall" → NLB. "Route /api to one service and /images to another" → ALB (path-based routing). "Inspect all traffic with a third-party appliance" → Gateway Load Balancer.

Things all ELBs do

  • Cross-zone load balancing — spreads to targets in every enabled AZ, not just the one that received the connection. Always on and free for ALB; off by default on NLB and chargeable when enabled.
  • Health checks decide what "healthy" means. Point them at a route that actually tests the app (a /health that touches the DB), not at a static file, or you will happily route to a broken instance.
  • TLS termination using an ACM certificate (free, auto-renewing, for use on ELB/CloudFront/API Gateway). SNI lets one listener serve many certificates.
  • Connection draining / deregistration delay (default 300 s) lets in-flight requests finish before a target is removed. Lower it if a question complains that scale-in is slow.
  • Access logs to S3 — off by default; the answer to "we need a record of every request".
  • The load balancer must live in subnets in ≥2 AZs, each with at least a /28 and enough free IPs.
Sticky sessions

ALB can pin a user to one target with a cookie (AWSALB for duration-based, AWSALBAPP for application-based). It works, but the exam prefers you remove the need for it — push session state to ElastiCache or DynamoDB so any instance can serve any user. If an option offers "store session state externally", it usually beats "enable stickiness".

Where did the client's IP go?

Behind an ALB the app sees the ALB's IP; the real client is in the X-Forwarded-For header. An NLB in instance target mode preserves the client IP natively. This is the answer whenever logs "show the load balancer's address instead of the user's".

Auto Scaling groups

An ASG is defined by a launch template (what to launch), a set of subnets (where — use one per AZ, ≥2), and min / desired / max. It replaces unhealthy instances automatically, which is half of what "self-healing" means on the exam.

Useful metric targets: ASGAverageCPUUtilization, ALBRequestCountPerTarget (better for request-bound apps than CPU), or a custom metric such as SQS ApproximateNumberOfMessagesVisible per instance — the standard answer for scaling workers off a queue.

"Scaling reacts too slowly"

Ranked fixes: (1) shorten boot time with a golden AMI or an ASG warm pool; (2) switch to predictive or scheduled scaling if the pattern is known; (3) reduce the cooldown / use target tracking instead of simple scaling; (4) scale on a leading indicator (request count, queue depth) rather than a lagging one (CPU).

Lifecycle hooks and health

  • Lifecycle hooks pause an instance in Pending:Wait or Terminating:Wait so you can bootstrap it or drain/copy logs off it before it disappears.
  • Set the ASG's health check type to ELB (not just EC2) so an instance that boots but serves 500s gets replaced. EC2 health checks only see the hypervisor.
  • Termination policy default: balance across AZs first, then oldest launch template, then closest to the next billing hour.
  • Instance refresh rolls the fleet onto a new launch template version with a minimum healthy percentage — the answer to "deploy a new AMI with no downtime".
  • Suspend the ReplaceUnhealthy or Terminate processes when you need to debug an instance without the ASG killing it.

Note the minimum of 2, one per AZ: with min=1 an AZ failure means an outage while the replacement boots. "Minimum two, spread over two AZs" is the resilient answer.

Check yourself

Users are logged out at random after a scale-out event. Best fix?
Session state is local to each instance. Move it to ElastiCache (Redis) or DynamoDB so any instance can serve any request. Enabling ALB stickiness is a workaround that still loses sessions whenever an instance is replaced.
A partner will only call your service if you give them fixed IP addresses. What do you put in front?
A Network Load Balancer — it gets a static IP per AZ and supports Elastic IPs. If you also need layer-7 routing, put an ALB behind the NLB as a target.
Traffic reliably triples at 09:00 every weekday, and target tracking is always five minutes late.
Scheduled scaling to raise the desired capacity just before 09:00 (or predictive scaling). Combine with a shorter boot time via a golden AMI or warm pool.
An instance passes EC2 status checks but returns HTTP 500. The ASG leaves it running. Why?
The ASG health check type is EC2, which only sees hypervisor-level health. Set it to ELB so the target group's application health check drives replacement.

Take away

  1. ALB = HTTP with content-based routing. NLB = layer 4, extreme scale, static IPs. GWLB = insert third-party appliances.
  2. ASG + ELB across ≥2 AZs with min ≥ 2 is the baseline "highly available" answer.
  3. Target tracking is the default scaling policy; scheduled/predictive for known patterns; queue depth for workers.
  4. Set ASG health checks to ELB, or broken-but-running instances stay in service.
  5. Prefer externalised session state over sticky sessions.
  6. Real client IP lives in X-Forwarded-For behind an ALB; an NLB preserves it natively.
