One distinction carries more exam marks than anything else in this lecture: Multi-AZ is for availability, read replicas are for performance. Get that reflexive and most RDS questions collapse to one obvious answer.

What RDS gives you

Managed MySQL, PostgreSQL, MariaDB, Oracle, SQL Server and Db2: AWS handles provisioning, OS and engine patching, automated backups, monitoring and failover. You lose SSH access to the host — which is why "we need OS-level access to the database server" means EC2, not RDS.

  • Automated backups: daily snapshot + transaction logs every 5 minutes, retained 1–35 days, enabling point-in-time recovery to any second in the window. Deleted with the instance unless you take a final snapshot.
  • Manual snapshots: kept until you delete them, can be copied cross-Region and shared with other accounts. This is how you do RDS DR.
  • Encryption at rest via KMS must be chosen at creation. To encrypt an existing unencrypted instance: snapshot → copy the snapshot with encryption → restore. In transit: TLS.
  • Storage autoscaling grows the volume when it fills. Performance Insights and Enhanced Monitoring diagnose slow queries.
  • RDS Proxy pools and shares database connections — the answer for Lambda exhausting the connection limit, and it also cuts failover time and can enforce IAM auth.
  • IAM database authentication issues 15-minute tokens instead of passwords; otherwise store credentials in Secrets Manager with automatic rotation.

Read the requirement, pick the feature

"Survive an AZ failure with no manual intervention" → Multi-AZ. "Reporting queries are slowing down the application" → read replica. "Both" → enable both; they compose. "Survive a Region failure" → cross-Region read replica (or Aurora Global Database). Any answer offering read replicas as a high-availability solution, or Multi-AZ as a performance solution, is a distractor.

Failover happens automatically on AZ outage, instance failure, storage failure, or during patching and instance-class changes — which is why Multi-AZ also reduces maintenance downtime. Because the endpoint DNS name stays the same, applications reconnect rather than reconfigure.

Aurora

AWS's own MySQL- and PostgreSQL-compatible engine, up to 5× MySQL / 3× PostgreSQL throughput. Its architecture is the thing to understand:

  • Storage is a shared, distributed volume that automatically keeps 6 copies across 3 AZs. It grows in 10 GB steps up to 128 TB and self-heals. Writes survive losing 2 copies; reads survive losing 3.
  • Compute is separate: one writer and up to 15 readers, all reading the same storage — so replicas add no replication lag from copying data and failover is typically under 30 seconds.
  • Endpoints: cluster (always the writer), reader (load-balances across replicas), custom (a named subset of instances). Point the app at the reader endpoint for read traffic — don't hardcode instances.
  • Backtrack rewinds a cluster in place to a point in time without restoring a snapshot — the "undo a bad migration quickly" answer.

Aurora replicas do two jobs

An Aurora replica is simultaneously a read-scaling instance and a failover target — no separate standby is needed. That is why "Aurora with replicas in multiple AZs" satisfies both availability and read-scaling requirements in one answer, and why Aurora often beats RDS Multi-AZ + read replicas in a "most resilient and most performant" question.

Check yourself

Nightly BI reports make the production database slow. Multi-AZ is already on.
Add a read replica and point the reporting tool at it. Multi-AZ's standby cannot serve reads, so it does nothing for this problem.
A Lambda-based API intermittently fails with "too many connections" against Aurora.
RDS Proxy. Thousands of concurrent Lambda invocations each open a connection; the proxy pools and multiplexes them, and also shortens failover.
A relational workload must survive the loss of an entire Region with RPO under a second and RTO around a minute.
Aurora Global Database. Cross-Region read replicas on standard RDS have higher lag and slower manual promotion; Multi-AZ doesn't cross Regions at all.
A dev database is used for two hours a day and idle otherwise. Cut cost without deleting it.
Aurora Serverless v2, which scales capacity down when idle. (For plain RDS, stopping the instance works but it restarts automatically after 7 days.)

Take away

  1. Multi-AZ = synchronous, automatic failover, not readable — availability. Read replicas = asynchronous, readable, manual promotion — performance.
  2. Cross-Region DR for relational data = cross-Region read replica, snapshot copy, or (best) Aurora Global Database.
  3. Aurora: 6 copies across 3 AZs, up to 15 replicas that double as failover targets, sub-30-second failover, reader endpoint for load balancing.
  4. Aurora Serverless v2 for spiky or intermittent load; Backtrack to undo mistakes without a restore.
  5. RDS Proxy solves Lambda connection exhaustion and speeds failover.
  6. Encryption must be set at creation — otherwise snapshot, copy encrypted, restore.
  7. Need OS access → EC2 or RDS Custom, not standard RDS.
