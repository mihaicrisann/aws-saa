A managed key-value and document database with single-digit millisecond latency at any scale, no servers, and no capacity planning if you don't want it. The exam tests three things: when to choose it, how keys work, and which capacity mode.

Keys and items

ConceptMeaning
Partition key (PK)Hashed to choose a physical partition. Alone, it must be unique.
Sort key (SK)Optional second half of a composite key. Items with the same PK are stored together, ordered by SK — which is what makes Query fast.
ItemA row. Max 400 KB — larger payloads go to S3 with a pointer stored here.
AttributeA field. Schemaless apart from the key.
Hot partitions

Throughput is spread across partitions by the partition key. A low-cardinality key (status = "active", or today's date) concentrates all traffic on one partition and causes throttling even though the table's provisioned capacity looks fine. The fix is a high-cardinality key — user id, order id, or a key with a random suffix (write sharding). Any question describing throttling on part of a table is about this.

Query fetches items by partition key (optionally narrowed by sort key) — fast and cheap. Scan reads the entire table then filters — slow and expensive, and always the wrong answer when a Query or an index would do.

Capacity modes

BillingPer requestPer RCU/WCU per hour
Choose whenUnpredictable / spiky / brand-new workloads, or you don't want to think about itSteady, predictable traffic — considerably cheaper, and eligible for reserved capacity
ScalingInstant, automaticAuto scaling adjusts within a min/max band

Capacity unit arithmetic, in case it's asked: 1 RCU = one strongly consistent read of up to 4 KB per second, or two eventually consistent reads. 1 WCU = one write of up to 1 KB per second. Reads are eventually consistent by default; ask for strong consistency and you pay double.

The GSI throttling trap

A GSI has its own provisioned capacity. If the GSI is under-provisioned, writes to the base table are throttled — because DynamoDB must write the index entry too. "Writes started failing after we added an index" is this, every time.

Choosing DynamoDB over a relational database

SQL or NoSQL?
Complex joins, transactions across many tables, ad-hoc reporting queries→RDS / Aurora
Known access patterns, key-based lookups, massive scale, unpredictable spikes→DynamoDB
Session state, user profiles, shopping carts, IoT device state, leaderboards→DynamoDB (the classic exam scenarios)
"Serverless", "no capacity planning", "single-digit ms at any scale"→DynamoDB — this is its marketing vocabulary and the exam uses it

Check yourself

A table is throttled although consumed capacity is well below provisioned.
A hot partition — the partition key has too few distinct values, so one partition absorbs the traffic. Redesign to a higher-cardinality key, or shard writes with a random suffix. Alternatively an under-provisioned GSI is throttling the base table's writes.
Reads must drop from milliseconds to microseconds with no application rewrite.
DAX — a DynamoDB-native, write-through cache cluster that the DynamoDB SDK talks to transparently.
The team needs to query on email, but the table's key is userId, and the table is already live in production.
Create a GSI with email as the partition key. An LSI is impossible — LSIs can only be created with the table.
Users in three continents need low-latency reads and writes on the same data.
DynamoDB Global Tables — multi-Region, multi-active replication with last-writer-wins conflict resolution.

Take away

  1. High-cardinality partition keys, always. Hot partitions are the number one DynamoDB question.
  2. Query, don't Scan.
  3. On-demand for unpredictable, provisioned (+ auto scaling) for steady and cheaper.
  4. GSI: any key, any time, own capacity, eventually consistent. LSI: same PK, creation time only, shares capacity.
  5. DAX for microsecond reads; Streams to react to changes; Global Tables for multi-Region active-active; TTL to expire data for free.
  6. Items cap at 400 KB — anything bigger lives in S3 with a pointer in the table.
