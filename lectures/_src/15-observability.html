Three services get confused with each other constantly, and the exam knows it: CloudWatch watches performance, CloudTrail records who did what, Config records how things are configured. Fix that sentence in your head and this domain gets easy.

CloudWatch

  • Metrics at 5-minute granularity by default; detailed monitoring gives 1 minute (chargeable). Custom metrics can go to 1-second high resolution.
  • Memory and disk usage are not default EC2 metrics — the hypervisor can't see inside the guest. You must install the CloudWatch agent. This is a favourite question.
  • Logs: log groups with retention (default: never expire — set one, or the bill grows forever). Logs Insights queries them with a purpose-built query language. Metric filters turn a log pattern into a metric you can alarm on (e.g. count of "ERROR" or of root logins).
  • Alarms have states OK / ALARM / INSUFFICIENT_DATA and act on SNS, Auto Scaling, or EC2 actions (stop/terminate/reboot/recover). Composite alarms combine several to cut noise.
  • Synthetics canaries script user journeys from outside to catch problems before users report them. RUM collects real user telemetry. Container Insights / Lambda Insights for those runtimes.
  • EventBridge (formerly CloudWatch Events) carries the event stream side of this.

CloudTrail

  • On by default, keeping 90 days of management events in Event History. For longer retention or analysis you create a trail delivering to S3 (and optionally CloudWatch Logs).
  • Management events = control-plane operations (create/delete/modify). Data events = high-volume object-level operations (s3:GetObject, lambda:Invoke) — off by default and chargeable. "We need to know who read that S3 object" → enable data events.
  • An organization trail captures every account centrally. Enable log file validation and lock the destination bucket down (Object Lock, MFA delete) so the audit trail is tamper-evident — a standard compliance answer.
  • CloudTrail Insights detects unusual API activity patterns.
The classic three-way question

"An S3 bucket was made public last Tuesday. We need to know who did it, be alerted next time it happens, and automatically fix it." → CloudTrail tells you who. Config with the s3-bucket-public-read-prohibited rule detects and, with a remediation action (an SSM Automation document), fixes it. EventBridge + SNS alerts. All three, each doing its own job.

AWS Config

Records the configuration of every supported resource over time, so you can ask "what did this security group look like on 3 March?" and "which resources violate our rules right now?". Managed rules cover most common checks; custom rules run a Lambda. Conformance packs bundle rules; aggregators roll compliance up across accounts and Regions; remediation actions fix violations automatically.

Two easy marks

"Centrally manage and enforce backup policies across accounts" → AWS Backup. "Prevent any account in the organisation from using a Region or disabling CloudTrail" → an SCP, not an IAM policy — IAM policies live inside one account and an administrator there could simply remove them.

Check yourself

You need an alarm on EC2 memory utilisation. It isn't in the metric list.
Memory is a guest-OS metric. Install the CloudWatch agent on the instances to publish memory and disk as custom metrics, then alarm on those.
Someone terminated a production instance. Find out who, and be alerted next time.
CloudTrail event history (or the trail in S3, queried with Athena) shows the identity, time and source IP. For alerting, an EventBridge rule on the TerminateInstances event → SNS. A CloudWatch Logs metric filter + alarm on the CloudTrail log group is the equivalent older answer.
Auditors require that every EBS volume in every account is encrypted, continuously, with automatic fixes.
AWS Config rule encrypted-volumes, deployed org-wide via a conformance pack and an aggregator, with a remediation action. Add an SCP denying the creation of unencrypted volumes so it cannot recur.
Store a database password with automatic 30-day rotation.
Secrets Manager — it has built-in rotation with Lambda and native RDS integration. Parameter Store SecureString is free but does not rotate on its own.

Take away

  1. CloudWatch = performance and logs. CloudTrail = who called what API. Config = configuration state and compliance over time.
  2. EC2 memory and disk need the CloudWatch agent; CloudTrail data events need enabling explicitly.
  3. Config rules + remediation actions is the "detect and auto-fix misconfiguration" answer.
  4. Session Manager replaces bastions; Parameter Store is free config, Secrets Manager rotates.
  5. SCPs are org-wide guardrails that a local administrator cannot remove; IAM policies are not.
  6. Control Tower for a new multi-account landing zone; AWS Backup for central backup policy.
