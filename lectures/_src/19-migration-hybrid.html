Two families of question live here. Migration: something exists elsewhere and has to end up on AWS — the exam asks which service moves it and how much downtime that costs. Hybrid and edge: something cannot leave the building or cannot tolerate the latency of a Region — the exam asks which box AWS ships you. Both are decided by one or two words in the scenario.

Moving bytes: the bandwidth question

Before any service name, work out whether the data can travel over the wire in the time allowed. That single calculation eliminates half the options.

The arithmetic the exam expects

A useful rule: 100 Mbps moves roughly 1 TB per day at full utilisation. So 500 TB over a 1 Gbps link that is also carrying production traffic is months, not days — Snow. And 2 TB over the same link is an afternoon — DataSync. If the scenario gives you a link speed and a deadline, it wants you to do this sum.

Snowball Edge is two products

If the scenario only moves data, Storage Optimized. If it mentions running anything at the remote site — analytics, machine learning inference, filtering before upload — it wants Compute Optimized. Reading past that word is the classic loss here.

Database Migration Service (DMS)Moves the data, and keeps the source live throughout"Minimal downtime", "continue serving during the migration"

Homogeneous vs heterogeneous — a guaranteed question

Homogeneous = same engine either side (Oracle → RDS for Oracle, MySQL → Aurora MySQL). DMS alone; the schema already fits.

Heterogeneous = the engine changes (Oracle → Aurora PostgreSQL, SQL Server → MySQL). SCT first to convert the schema, then DMS to move the data. If an option offers DMS by itself for a cross-engine move, it is incomplete.

DMS also does continuous replication (CDC), which is what "cut over with almost no downtime" is buying.

Migrating applications into containers

The exam frames this as a trade between effort now and cost later. Learn the ladder and match it to the qualifier.

ApproachWhat changesLands onChosen when the scenario says
RehostNothingEC2 via MGN"Fastest migration", "no code changes", a hard deadline
ReplatformPackaging only — the app is containerised as-isECS on Fargate, or EKS if they already run Kubernetes"Reduce operational overhead", "without rewriting the application"
RefactorThe architectureLambda, Step Functions, managed services"Re-architect", "event-driven", and no time pressure
ECS or EKS

Once containerised, the default is ECS on Fargate — no cluster to run, no nodes to patch. Pick EKS only when the scenario names Kubernetes, existing Helm charts, or a need to keep the same tooling on-premises. ECS Anywhere and EKS Anywhere run those control planes against your own hardware, which is the answer when containers must keep running in a data centre you are not leaving.

Hybrid and edge compute

Four boxes, four different reasons. The reason is always stated in the scenario.

OptionWhere it runsThe words that select it
OutpostsA rack of genuine AWS hardware in your data centre, same APIs"Data must remain on premises" for residency or regulation, or single-digit-millisecond latency to on-premises systems, while still using AWS services
Local ZonesAn AWS-run site in a metro area, close to users"Single-digit-millisecond latency to users in a specific city" — media editing, gaming, remote workstations
WavelengthInside a telecoms provider's 5G networkThe scenario says 5G or mobile devices needing ultra-low latency
VMware Cloud on AWSVMware's own stack on dedicated AWS hosts"Keep using vSphere / vCenter", "existing VMware skills and tooling"
Do not confuse edge compute with the edge network

CloudFront and Global Accelerator put traffic closer to users. Local Zones, Wavelength and Outposts put your compute and data closer. A question about caching static assets is CloudFront; a question about an application server that must sit within 5 ms of a factory floor is Outposts.

Check yourself

900 TB of archives must reach S3 within a month. The site has a 500 Mbps internet link shared with production.
Snow. At 500 Mbps you would move roughly 5 TB a day if you saturated the link, so 900 TB is around six months — and you cannot starve production. Order a cluster of Snowball Edge Storage Optimized devices. Direct Connect fails on lead time as well as throughput.
An Oracle database moves to Aurora PostgreSQL with the business running throughout.
SCT then DMS. The engines differ, so the Schema Conversion Tool converts schema, views and stored procedures first; DMS then does a full load followed by change data capture, so the source stays live until a short cutover.
A hospital must run a patient application on AWS services but is legally barred from letting the data leave its premises.
Outposts. It is the only option that puts real AWS infrastructure and APIs inside their own data centre. Local Zones and Wavelength are AWS-operated sites — the data still leaves the building.
A monolith on ageing VMs must reach AWS this quarter with no code changes, then cut operational cost.
Two steps, and the exam rewards saying so: rehost with MGN to hit the deadline, then replatform onto ECS with Fargate to remove the servers. Refactoring to Lambda is the right long-term answer to a different, unhurried question.

Take away

  1. Do the bandwidth sum first — roughly 1 TB per day per 100 Mbps. It eliminates half the options before you read them.
  2. DataSync moves files online; Storage Gateway keeps on-premises access permanent; Transfer Family is the SFTP endpoint; Snow is the courier.
  3. Snowball Edge Compute Optimized is the answer whenever anything is processed at the remote site.
  4. Same engine → DMS alone. Different engine → SCT then DMS. CDC is what buys near-zero downtime.
  5. Rehost with MGN for speed, replatform onto ECS Fargate to cut overhead, refactor to serverless only when time allows.
  6. Residency → Outposts. Metro latency → Local Zones. 5G → Wavelength. vSphere → VMware Cloud on AWS. Disconnected → Snow.
